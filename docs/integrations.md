# 自動連携の仕組み

24系統のうち、来訪・滞在・飲食・徒歩・自転車・自動車・勤務はコア機能で判定します。
残る17系統は `server/adapters.lua` が既存サーバー内通知を購読します。
既存の関数・イベントハンドラーを置換せず、既存リソース・DBには書き込みません。

## 精算通知

`pv_poe:job:complete(source, resourceName, payout)` を、設定された発火元リソースからだけ受け取ります。
このイベント名は既存連携用ですが、同名の管理リソース自体の起動は必要ありません。
発火元がジョブのコード内で直接通知します。

バス・ごみ回収・電気・郵便・タクシー・現金輸送・釣り・狩猟・Urideでは、さらにQbox自身が発火する
`QBCore:Server:OnMoneyChange` の正の入金と照合します。
同一キャラクター・同額・2秒以内という条件で入金通知を一度だけ消費し、
タクシー・釣り・Urideは入金理由も限定します。配布するクエスト報酬の入金は除外します。
この照合は既存の業務完了判定を信頼する方式で、業務ID付きの厳密なトランザクション照合ではありません。
バス・ごみ回収・電気・郵便・現金輸送では、通常精算とジョブ内ボーナスをどちらも対象にします。
同じ活動の30秒以内の連続通知は、後述のクールダウンで追加加算しません。

Urideはfr-rideの運転手への入金理由 rideshare-earning / npc-mission-reward を対象にします。
乗客の運賃支払い、通知だけ、別リソースからの同名通知は加算しません。

建築と清掃は、精算ラッパーでなく完了専用フックに置かれた通知を受け取ります。
清掃の完了通知は金額が省略される場合もあるため、正の金額を必須にはしていません。

## 個別の完了通知

| 活動 | 発火元 | 通知 |
| --- | --- | --- |
| リサイクル | jim-recycle | skybp:mining:done |
| ブースティング | gg_boosting | skybp:boostComplete |
| 家強盗 | satou_houserobbery | satou_houserobbery:server:completed |
| カーゴ強盗 | lunar_heistcontracts | lunar_contracts:heistCompleted（cargo契約のみ） |

`skybp:` という名前でも、発火元はジョブ自身です。`skybp_events` の起動状態にかかわらず受信できます。
家強盗の参加者は通知を受けた時点でcitizenidに結び付け、DB待機中のsource再利用による誤加算を防ぎます。
カーゴは契約名がcargoの成功通知だけを受け付けます。membersに含まれるcitizenidを接続中の本人に結び付け、
DB待機前に全参加者を確定します。同じ参加者は1回だけ加算し、所有者でもmembersに含まれない場合は加算しません。
他の契約・途中の戦利品取得・クライアントからの同名通知は対象外です。satou_loggingへの依存はありません。

## ATM強盗・コンビニ強盗の戦利品取得

対象はprojectx-atmrobberyと、projectx-storerobberyを置き換えるsatou_storerobberyです。
対応済みox_inventory内で動く通知ブリッジのsatou_logging:inventoryを購読し、
アイテム追加に成功した後の通知だけを使います。サーバー内イベントの発火元がox_inventoryで、
元の付与リソースが対象と一致し、本人のインベントリにblack_moneyが正の個数で追加された場合に1回加算します。
通知のキャラクターIDと現在の接続者を照合し、再接続によるsource再利用は拒否します。

同じ付与が複数スロットに分かれても1回です。コンビニはレジ・店内ATM・金庫などの取得単位で、
店舗全体の攻略回数ではありません。60秒以内の連続獲得は追加加算しません。
部品、ATM本体、コイン、アイテム譲渡、管理者付与、失敗して所持品が増えなかった操作は対象外です。

この2活動には、対応済みox_inventory通知ブリッジとsatou_loggingの起動が必要です。
satou_logging停止時は新しい抽選から除外し、提示済み・デバッグ一覧にも連携元未起動を表示します。
当リソースはログDBを参照・変更せず、調査用ログも追加しません。
標準版ox_inventoryにこの通知があるとは限りません。

## 重複と障害

通知に一意の完了IDがないため、`suimag_dailyquest_signal_gates` のキャラクター／活動別ロックで
クールダウンと日次・週次の加算を1トランザクションにします。
同時通知・再起動・日付境界・同じSQLの再送で追加加算しないことを実MariaDBで検証しています。
ゲートは他の既存テーブルを参照しません。

DBエラーで結果不明の既存イベントは自動再送しません。入金との照合に失敗した精算も加算しません。
通知の完了IDを持たないため、クールダウンより後の同じ通知の再送を完全に識別することはできません。

## 導入・更新時

- 連携元が起動していても、この環境固有の通知が削除・変更されると進捗は届きません。
  各ジョブを更新した際は [クエスト一覧](catalog.md) の代表操作を1回ずつ確認してください。
- 標準配布の同名リソースに必ずこれらの通知があるとは限りません。今回確認した資材の通知契約に合わせています。
- 連携コードが不明な環境へ、クライアント申告イベントの購読で代用しないでください。
- 既存リソースを自動で停止／再起動することはありません。
- 詳細なサーバー調査記録や購入ソース一式は公開リポジトリへ収録していません。

提示中の割当がない進捗更新はSQLでも拒否します。属性変更だけで割当は変わりません。抽選前の行動は遡及しません。

## 連携元の修正パッチ

[最小差分](../patches/job-integrations.patch)と[回帰テスト](../tests/integration_resources_spec.lua)を用意しています。
対象は次の3件です。調査用ログやデバッグ準備ボタンは含みません。

- 釣り: Qboxへの入金理由を引き継ぎ、魚・カニの売却を照合できるようにする。
- タクシー: 精算対象がない場合は中断し、参照エラーや不要な次回依頼の生成を防ぐ。
- 家強盗: 参加者が実際に戦利品を取得した場合だけ、ホスト脱出を成功として通知する。

確認済み資材向けの差分です。購入リソース本体は各自用意し、まずローカルコピーで適用してください。
コピーの直下に `[whitejob]` と `[robbery]` がある構成を想定しています。
文脈を含めない最小差分のため、適用前のSHA-256照合に失敗した場合は適用せず、資材の版を確認します。
パッチはLFとCRLFを保持しているため、改行変換せず使用してください。

```bash
DQ_REPO=/path/to/suimag-dailyquest
cd /path/to/local-resource-copy
sha256sum -c "$DQ_REPO/patches/job-integrations.before.sha256"
# 上の4ファイルがすべてOKの場合だけ続行
patch --batch --forward --fuzz=0 --binary -p1 -i "$DQ_REPO/patches/job-integrations.patch"
sha256sum -c "$DQ_REPO/patches/job-integrations.after.sha256"
cd "$DQ_REPO"
lua tests/integration_resources_spec.lua /path/to/local-resource-copy
```

回帰テストは対象資材の実コードを読み込み、外部APIを模擬して検証します。
購入リソースが必要なため、CIではこのテストファイルの構文確認のみを行います。
パッチの追加や本リポジトリの更新だけでは、サーバーへの反映・リソース再起動は行いません。
